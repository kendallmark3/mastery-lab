# INTENT-001 — Mastery Lab: First Complete Learning Loop

**Project:** Mastery Lab  
**Version:** POC 0.1  
**Type:** Intent-driven build specification for Claude Code  
**Status:** Ready to implement  
**Guiding principle:** **AI for Humans — Learn. Teach. Master.**

## 1. Intent — WHY and WHAT

Build the smallest *working* learning capability that helps a person move from **asking an AI a question** to **demonstrating what they can actually do**.

The first proof of concept must enable one learner to complete a full cycle:

**Set learning goal → receive a practical challenge → submit an answer or artifact → receive evidence-grounded feedback → save progress → resume later.**

This is **not** a new general-purpose AI tutor or a chat clone. Claude or another capable assistant supplies conversational intelligence; Mastery Lab supplies the persistent learning records, challenge structure, evidence, and tools that assistants otherwise lack.

Build it initially for **one local user**. Commercialization, subscriptions, and App Store distribution are not goals.

## 2. Inputs / Context

### Operating philosophy

- **AI for Humans:** Optimize for demonstrable improvement in human capability, not the number of AI features.
- **Intent-Driven Engineering:** The human specifies outcomes, constraints, and success criteria; AI determines the implementation.
- **The Bitter Lesson:** Prefer simple, general approaches. Avoid hardcoded teaching intelligence, unnecessary workflow engines, and premature agents.
- **Extend AI; do not duplicate it:** Provide a reusable capability that AI assistants can use, rather than embedding a second chatbot merely to duplicate their responses.
- **Evidence before mastery claims:** Clearly separate what was submitted, what was observed, and what an evaluator inferred.

### Initial learner and subject

- Learner: one developer / AI architect using the system personally.
- Starting domain: **Enterprise AI Architecture**.
- Example learning goal: *Design governed AI systems that retrieve enterprise data and execute approved actions.*
- Seed scenario: *A regulated enterprise needs an AI assistant that retrieves controlled documents and proposes or executes approved business actions. Design the system boundaries, access controls, auditability, and failure behavior.*
- An excellent first response need not be a full diagram; a structured written architecture is acceptable.

### Preferred deployment posture

- **Local-first** for the first iteration; no AWS account, paid model API, or production cloud environment should be required to demonstrate the full loop.
- A **minimal browser interface** should make the POC usable even without an assistant connector.
- Expose the core operations through a **standards-based MCP server** so a compatible AI client can use the same learning records and tools.
- Reuse the same application/domain logic behind the UI, HTTP API (if exposed), and MCP tools. Avoid creating separate learning engines.
- Python is preferred because it supports our learning and AI architecture goals; FastAPI and a lightweight persistent store such as SQLite are reasonable defaults, but implementation details are Claude's decision.

## 3. Outputs — What must exist when finished

Deliver a runnable repository containing:

1. **A working local web experience** where one learner can create or choose a learning goal, open a challenge, submit an answer, inspect feedback, view progress, and resume a previous session.
2. **Persistent structured records** for learner goals, challenges and their explicit evaluation criteria, submissions, feedback, evidence references, and session history. Data must survive process restarts.
3. **A minimal MCP surface** through which a compatible AI client can retrieve the learner's context, present/create a challenge, record a submission, record evidence-linked feedback, and report recommended next practice. Use the currently supported Python MCP SDK and document how to connect a compatible client; do not claim a ChatGPT or Claude integration is active unless actually tested.
4. **One meaningful seed challenge** on governed enterprise AI architecture, with clear success criteria and enough context to practice.
5. **An honest feedback mechanism.** Feedback should refer to specific submitted content and criteria, distinguish verified observations from judgments, and mark unsupported claims as unverified. It may be generated by a connected AI assistant through MCP, with a manual/structured feedback path in the browser so the complete local POC never requires an API key. Do not present a numeric mastery score as objective proof.
6. **Automated tests** covering the learning loop, record persistence, missing/invalid inputs, and evidence/feedback linkage.
7. **README** with prerequisites, one-command-or-few-command local startup, a five-minute demonstration script, MCP connection instructions, and explicit limitations.

## 4. Success Criteria — Observable acceptance evidence

The POC is complete only when all of the following are demonstrably true:

- **SC-01 — Start:** I can create or select the Enterprise AI Architecture learning goal and begin a challenge.
- **SC-02 — Practice:** I receive a concrete scenario with a deliverable and explicit, visible evaluation criteria; it is more substantial than a multiple-choice quiz.
- **SC-03 — Submit:** I can submit my own written solution; the saved record is associated with the correct goal and challenge.
- **SC-04 — Evaluate:** I can obtain or enter criterion-by-criterion feedback citing actual submission evidence, noting gaps and uncertainties without pretending unverified claims are proven.
- **SC-05 — Persist:** I can close the program, restart it, return to the same goal, and view the earlier challenge, submission, feedback, and suggested next step.
- **SC-06 — Reuse:** The same underlying records and operations work via both the local browser interface and the MCP tool surface; demonstrate at least one real MCP tool round-trip using an SDK-compatible client/test harness.
- **SC-07 — Trust:** An empty submission, nonexistent challenge, and an attempt to save feedback referencing invalid evidence are rejected clearly; data is never silently misattributed.
- **SC-08 — Reproduce:** A fresh checkout can be installed and run from the README, and the automated tests pass.

**Evidence of completion:** Provide the actual commands run, test results, screenshots or a brief UI walk-through, an MCP round-trip transcript, and any known failures. Do not substitute an architecture description for working code.

## 5. Constraints, Boundaries, and Non-goals

### Must-have boundaries

- Keep the first implementation **small, working, and understandable**. Prefer a vertical slice over scaffolding a large platform.
- No paid services, model API key, cloud deployment, user registration, payment processing, or mobile app required.
- Keep the app local-only by default. If an HTTP endpoint is exposed, bind to loopback by default and clearly document that it is **not production-ready**; do not imply multi-user authorization or compliance controls exist.
- Minimize personally identifying or sensitive data. Treat uploaded/submitted work as user-controlled local data; avoid sending it to external services without the user's explicit action.
- Preserve the provenance of feedback: who or what provided it, which challenge criterion it addresses, and which portion of the submission supports it. When evidence is incomplete, say so.
- Avoid a false distinction between a solution being *well argued* and its effectiveness being *proven in operation*.

### Explicitly out of scope for INTENT-001

- Autonomous multi-agent orchestration, LangGraph, and elaborate curriculum planning.
- Fine-tuning, vector databases, elaborate RAG, or building a replacement AI chat experience.
- Gamification, leaderboards, social features, certificates, subscription tiers, and commercial analytics.
- AWS provisioning, iOS packaging, production authentication, enterprise compliance claims.
- Automatic validation of the operational correctness of every possible architecture design. For this first POC, carefully evidenced criterion-level assessment is enough.

## 6. Implementation Freedom

Claude Code owns the implementation plan, project structure, framework decisions, component boundaries, and UI layout within these constraints.

Prefer **minimum sufficient architecture**. If a simpler solution satisfies every success criterion, use it. If a requirement requires more complexity than anticipated, record the tradeoff rather than silently adding unrelated infrastructure.

Do not spend time asking about minor implementation preferences. Make reasonable decisions, implement, and document them. Ask only if a genuinely blocking dependency or irreversible tradeoff emerges.

## 7. Requested Execution Sequence

1. Inspect the working directory and determine whether this is a fresh project or an existing repository.
2. Write a brief implementation plan mapped to the success criteria; then **build the application**.
3. Seed the first enterprise AI architecture scenario with explicit evaluation criteria.
4. Exercise the full browser loop, persistence across restart, and an MCP tool round-trip.
5. Run tests and fix failures.
6. Report what was built, where it runs, how to demo it, actual validation evidence, limitations, and the **smallest evidence-driven recommendation for INTENT-002**.

**Stop condition:** Do not expand to cloud hosting, mobile, multi-user features, or speculative infrastructure when INTENT-001's acceptance criteria are met.

## 8. Claude Code — Final Instruction

**Implement this intent as working code now, not merely a proposal.**

Begin with the smallest useful vertical slice. Preserve human ownership of intent and success criteria; use your judgment on the HOW. Treat every claimed outcome as something to demonstrate with evidence.

> **North Star:** Build the smallest capability that turns an AI-assisted conversation into demonstrable human learning.
